Workflow Components
	- Code that adds processing step to a workflow
	- Typically takes a stream as input, returns a stream
	- simplifies workflow code
	- refactoring cde

Segmenting Workflows
	- write the output of one segment to a sink
	Reasons to Segment
		- Different delivery requirements for intermediate results
		- Easier to update
		- Different teams can work on different segments
		- More fine grained resource management (e.g. differnet parallelism)

	Reasons not to Segment
		- Increased Latency
			- each bridge adds, on average, 1/2 of the checkpoint interval in latency
		- Increased Operational Overhead
			- Esch Workflow has to be monitored
			- each workflow has separate state
			- a major change can mean restarting N worflows
		- Schema management becomes critical
			- Data that is "handled off" via the bridge must be well documented
			- Schema evolution must be synchronized

		Hudi as a Bridge - low bus factor

In a nut shell, avro-fastserde enables faster Avro de/serialization by doing runtime code-generation to provide a faster decoder/encoder implementation.

As part of this fork, there are compatibility improvements to ensure that the decoding semantics are the same as that of regular Avro (in particular around the handling of String types in modern Avro). Finally, this fork provides supports for object re-use, a standard Avro deserialization feature, as well as some other garbage-collection optimizations which have proven useful at LinkedIn.
